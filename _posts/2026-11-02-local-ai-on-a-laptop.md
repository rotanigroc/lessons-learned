## The idea

An M1 Pro laptop with 32 GB of unified memory is a capable local-model host. I made it the primary development and AI machine: it serves local models, holds the master git checkouts, and runs the coding agent. A second laptop becomes a client that edits synced working trees.

## The pieces

| Piece | Mechanism | Direction |
|---|---|---|
| Working trees | One-time `rsync` seed (with `.git`), then a Mutagen session (without `.git`) | Client to hub once, then two-way |
| Agent chats and per-project memory | Mutagen session on the agent's projects directory | Two-way |
| Local LLM server | LaunchAgent on the hub, proxied by the reverse proxy; API key required | Hub serves, LAN clients call |
| Vault wrappers and skill | An installer script, run once | One-off |

Every script is read-only or dry-run until told otherwise.

## Why the sync is built the way it is

**Old idea:** sync everything, including `.git`, in both directions.

**New:** the seed copies `.git`; the ongoing sync does not.

- A sync tool's own documentation advises against syncing `.git`: the index is rewritten by `git status`, git does not expect concurrent writers, and garbage collection repacks. The recommended model is one master side. The hub is the master.
- A file-level seed also carries repos that have **no remote at all**, plus uncommitted work. `git clone` cannot move either. Several repos in this setup had no remote.
- The mode is `two-way-safe`: nothing is silently overwritten. A real conflict shows in a status command and waits for a human.
- **Same user and absolute paths on both machines.** The agent keys each chat directory by the working directory's absolute path, so the hub only sees those chats if it is the same user with the repos at the same paths. A `check` command enforces it.
- One ignore list drives both the seed and the sync: mount points, temp dirs, `node_modules`, virtual environments, Rust `target/` dirs, caches. One venv alone was 1 GB.
- Everything else travels, including `.env`-style files. That is a decision, not an accident: secrets in the working tree go over SSH like everything else, and the doc says so, with a note to add a pattern for anything that should not.

To keep the client's `git status` honest despite not syncing `.git`, a small LaunchAgent every 15 minutes fetches each repo's upstream and does a `git reset --mixed` to it. That moves the branch and index but never working-tree files, so the client's `git status` shows the hub's real uncommitted work. It skips repos with client-only commits, staged changes, a merge in progress or no upstream.

**Rule of use.** Run git and the agent on the hub. Flush before switching machines. Never resume the same chat on both at once.

## Serving models: MTPLX instead of Ollama

MTPLX is an MLX-native server for Apple Silicon with multi-token-prediction speculative decoding. It exposes OpenAI-style routes and an Anthropic-style `/v1/messages`, plus health and metrics.

The service is a per-user LaunchAgent (it needs the login session for Metal). Settings:

- The `sustained` profile, which suits a laptop. The default `turbo` profile runs hotter.
- **API key required** for any non-localhost bind. The key lives in a mode-600 file generated by the setup script and never printed (a missing key file makes the server print a fresh key once, which would land in a transcript).
- Bound to the LAN address, not `0.0.0.0`. Never port-forwarded.
- Model sizing on 32 GB: an 8.8 GB model leaves ample headroom, a 23.8 GB one leaves about 8 GB for macOS.

After a reboot with FileVault, it starts only once you log in. The doc says so rather than hiding it.

## Running Claude Code against a local model

A script switches the coding agent between the local backend and the cloud API by changing which base URL and key it uses. Warm-session results were recorded in the repo alongside it.

Two practical limits:

- The reverse proxy has a 240-second read timeout. A prompt that takes longer than that to prefill before the first token returns a 504. For very long contexts, call the server directly.
- The proxy needs response buffering off for streaming.

## The reasoning-model trap

The model replies with a *thinking* block that counts toward `max_tokens`. Measured:

| `max_tokens` | Result |
|---|---|
| 16 | Stopped inside the thinking block. **No text returned.** |
| 64 | Thinking plus the answer, `stop_reason: end_turn` |

Coding agents and most SDK clients set large limits, so this mostly bites hand-written test calls. When a quick test returns nothing, raise the limit before suspecting the server.

## Making a laptop behave like a server

A tuning script handles what a server needs and a laptop does not provide:

- **Sleep:** `pmset -c sleep 0 disksleep 0 womp 1 autorestart 1` while on power.
- **GPU memory:** raise the wired limit so a large model fits.
- **Spotlight:** exclude the model and repo directories from indexing.
- **Remote login:** on, for the one allowed user.
- **A static address** and, importantly, **DNS servers on the network service.** A manual-IP service with none resolves nothing. The bootstrap check warns about it.

Macs have no `nc` bridge by default for the desktop app's tool servers to reach the LAN, so small LaunchAgents bridge them.

## Small things that bit

- **The sync daemon.** A command to "autostart" the sync registered the daemon but did not start it. Fixed so it does both.
- **The wrong mode flag** in the sync config. Fixed, with a dry-run summary of the seed.
- **1Password's SSH agent** asks for approval per requesting process. The sync's background `ssh` timed out waiting for that click, and would again after every sleep or auto-lock. The fix: a dedicated unattended key just for the sync, restricted in `authorized_keys` by source subnet with no agent, port or X11 forwarding, and an SSH config block above `Host *` (first match wins) that tells that one host to skip the agent. Only that host skips it.
- **The service token cannot be synced.** The secrets service-account token lives in the keychain and has to be put on the hub by hand.

## Takeaways

- Pick one master for git and keep `.git` out of the live sync.
- Seed with files, not clones, if some repos have no remote.
- Make absolute paths and the user identical on both machines when state is keyed by path.
- A local server on a LAN address needs an API key, not a firewall hope.
- Reasoning models need a generous `max_tokens`. A tiny test limit looks like an outage.
- A laptop is not a server until you disable sleep, raise the memory limit and stop the indexer.
- Give background tools their own narrowly scoped key instead of fighting an agent that wants interactive approval.
